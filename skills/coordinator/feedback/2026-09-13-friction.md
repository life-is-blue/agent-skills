# Coordinator 摩擦点报告：abetl-front help-page goal（2026-09-13）

来源：本会话一次完整的 Tier 2 循环（tclaude 实现 / codex 验收 / worktree 隔离）。
回执见 `goals/help-page/README.md`。以下每条都是实际踩到的，附改进建议；没有硬凑。

## 1. Worker 的模型解析是主机设置的盲区

**现象**：`coding-agent-run --agent claude` 与 `--agent tclaude` 都以
`unrecognized_model {"model":"claude-kimi-k3[1m]","query_source":"sdk"}` 启动失败——
worker 经 SDK 继承了用户 `~/.tclaude/settings.json` 里的自定义模型 id，而子会话不识别它。
"Set up once per host" 一节只要求验证 CLI 存在与能力（`--help`、smoke），不要求验证
**worker 会话实际会解析到哪个模型**。绕行办法（`ANTHROPIC_MODEL=claude-sonnet-5` 环境变量）
是靠试错发现的，不在任何参考文档里。

**建议**：主机设置清单加一项"验证 worker 实际解析的模型 id"（一条最小 prompt 即可）；
或在 `coding-agent-run` 增加显式 `--model` 参数，并在 coding-agent 的 provider 参考里
记录 settings.json 模型会泄漏进 worker 这一事实。

## 2. retry/重派没有"确认旧会话已死"的前置条件

**现象**：实现者第二次派发的日志头部出现 unrecognized_model，我据此判定基础设施失败并
第三次派发到**同一 worktree**——实际上第二次派发的会话活着，并独立完成了全部实现。
两个实现者并发写同一 workdir，只因为两次派发用的是同一份冻结合成才没出事故。

**建议**：`retry` 的语义是"transport-level failure"，但判定依据留给 coordinator 的肉眼。
给 retry/重派加一条硬性前置：重派前必须用 runner `status`（或等价物）确认旧会话处于
终态；并在 durable-state/task-contract 参考里明确警告"两个存活派发不得共享同一 workdir"。
（本 goal 里 runner 的 `status` 命令存在且可用，是我没有调用。）

## 3. 验收沙箱与 loopback 门禁冲突时，verdict 会混淆环境与代码

**现象**：codex 在 `workspace-write` 沙箱里无法 bind 127.0.0.1，被验收项目的契约测试
（需起真实 HTTP）4 个子测试 EPERM 失败，验收官据此给出整体 REJECT——两条阻断理由都是
纯环境原因。裁决环节吸收了它（coordinator 在沙箱外复跑同一门禁 14/14），但
review-contract 参考没有提示这种冲突， verdict 的"FAIL 即代码问题"印象容易误导。

**建议**：review-contract 参考加一节"沙箱与门禁的匹配"：冻结验收合同前先确认验收沙箱
能否承载门禁的全部动作（loopback、浏览器、端口）；承载不了时，预先在合同里声明
证据替代路径（由 coordinator 在沙箱外复跑哪几条），让 REJECT 只表达代码问题。

## 4. runner 日志滞后导致会话健康误判

**现象**：实现者会话的 `log` 输出在很长一段时间里只有一行 unrecognized_model，但会话
实际在正常工作（worktree 里文件持续出现）。靠日志尾部判断存活不可靠——这正是摩擦 #2
的诱因之一。

**建议**：runner 的 `status` 输出增加心跳/最后活动时间戳（或 worker 侧定期写一行
progress marker），让"活着但安静"与"死了"可区分。

---

*非摩擦但值得记录的正面事实：冻结合同 + worktree 隔离在摩擦 #2 的并发事故中完全兜住了
产物完整性；验收暗卷（变异测试/XSS/诚实空态）全部一次通过，说明 withheld-checks 机制
对这类交付是有效的。*
